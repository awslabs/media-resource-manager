# Storage Management Feature Design Document

## Overview
Add comprehensive storage management functionality to the Media Resource Manager application, allowing users to create and manage AWS storage resources (FSx for Windows File Systems and AWS Storage Gateway File Volumes) through a simplified interface.

## Architecture Components

### 1. Frontend Components
- **New Page**: `StorageManagement.tsx` (based on `ImageManagement.tsx`)
- **Location**: `/home/ubuntu/media-resource-manager/frontend/src/pages/StorageManagement.tsx`
- **Features**:
  - Table view of storage resources
  - Create/Edit/Delete storage resources
  - Collection preferences and breadcrumb navigation
  - Property filtering and pagination
  - Modal dialogs for resource management

### 2. Backend Components - Microservices Approach

#### Lambda Functions (Following existing naming convention: [Purpose]Function)
- **ListStorageFunction** 
  - Location: `/home/ubuntu/media-resource-manager/lambda/list-storage/index.js`
  - Purpose: GET operations to retrieve storage resources

- **CreateStorageFunction**
  - Location: `/home/ubuntu/media-resource-manager/lambda/create-storage/index.js`
  - Purpose: POST operations to create new storage resources
  - Integrates with CloudFormation for FSx creation

- **UpdateStorageFunction**
  - Location: `/home/ubuntu/media-resource-manager/lambda/update-storage/index.js`
  - Purpose: PUT operations to update storage resource metadata

- **DeleteStorageFunction**
  - Location: `/home/ubuntu/media-resource-manager/lambda/delete-storage/index.js`
  - Purpose: DELETE operations to remove storage resources
  - Handles CloudFormation stack deletion

- **StorageStatusSyncFunction**
  - Location: `/home/ubuntu/media-resource-manager/lambda/storage-status-sync/index.js`
  - Purpose: Background function to sync CloudFormation stack status with DynamoDB
  - Triggered by CloudWatch Events or scheduled execution

#### API Gateway
- **New Resource Path**: `/storage`
- **Methods**: 
  - GET `/storage` → `ListStorageFunction`
  - POST `/storage` → `CreateStorageFunction`
  - PUT `/storage/{storageId}` → `UpdateStorageFunction`
  - DELETE `/storage/{storageId}` → `DeleteStorageFunction`

#### DynamoDB Table
- **Naming**: Uses kebab-case prefix from productName
- **Partition Key**: `storageId` (string)
- **Attributes**:
  - `storageId` (PK) - Unique identifier
  - `createdAt` - ISO timestamp (auto-generated by Lambda)
  - `name` - User-friendly name
  - `type` - Storage type ('fsx-windows' | 'storage-gateway')
  - `status` - Current status
  - `configuration` - Storage-specific configuration object
  - Additional schema to be defined later

### 3. Storage Resource Types

#### FSx for Windows File Systems
- **Configuration Options**:
  - Automatic Backup Retention Period (1-90 days, default: 30)
  - Throughput Capacity (32-12288 MB/s, predefined values)
  - SSD Storage Capacity (32-65536 GiB, default: 256)
- **Reference Template**: `/home/ubuntu/media-resource-manager/samples/mcs-fsx-template.json`

#### AWS Storage Gateway File Volumes
- **Configuration**: To be defined in future iterations
- **Integration**: Predetermined configurations for simplified user experience

#### Architecture Decision: Step Functions + Native Service Integrations

**Why Step Functions:**
- **CloudFormation Integration**: Native `cloudformation:createStack.sync` waits for completion
- **DynamoDB Integration**: Built-in DynamoDB actions for status updates (no Lambda needed)
- **Timeout Solution**: Step Functions can wait indefinitely for CloudFormation (45+ minutes)
- **Error Handling**: Automatic retry logic and failure cleanup
- **State Visibility**: Clear tracking of which step is executing
- **Atomic Operations**: All-or-nothing deployment with automatic rollback

**Why Native Service Integrations:**
- **No Lambda Overhead**: Direct DynamoDB updates without Lambda functions
- **Better Performance**: Fewer function invocations and cold starts
- **Cleaner Architecture**: Step Functions handles orchestration, Lambda only for business logic
- **Cost Effective**: Fewer Lambda invocations means lower costs

#### Updated GenerateFsxTemplateFunction Implementation

```javascript
// GenerateFsxTemplateFunction - Pass productName as CloudFormation parameter
exports.handler = async (event) => {
  const { storageId, name, configuration } = event;
  const productName = process.env.PRODUCT_NAME; // e.g., "Media Resource Manager"
  const stackName = `${productName}-Storage-${storageId}`;
  
  // Generate CloudFormation template with proper Fn::Join structures
  const template = generateFsxTemplate(storageId, configuration, productName);
  
  const parameters = [
    { ParameterKey: 'SSDStorageCapacity', ParameterValue: configuration.ssdStorageCapacity.toString() },
    { ParameterKey: 'ThroughputCapacity', ParameterValue: configuration.throughputCapacity.toString() },
    { ParameterKey: 'AutomaticBackupRetentionPeriod', ParameterValue: configuration.automaticBackupRetentionPeriod.toString() },
    { ParameterKey: 'ProductName', ParameterValue: productName }
  ];
  
  return {
    storageId,
    stackName,
    template: JSON.stringify(template),
    parameters
  };
};
```

#### Required SSM Parameters (New ProductName Prefix)

**Migration Strategy**: Create new SSM parameters using the pascalCase productName prefix while maintaining backward compatibility with existing `/MediaResourceManager` parameters.

**New Parameter Structure** (using `MediaResourceManager` as example):
- `/MediaResourceManager/Network/VpcId`
- `/MediaResourceManager/Network/PrivateSubnet1/SubnetID`
- `/MediaResourceManager/Network/PrivateSubnet2/SubnetID`
- `/MediaResourceManager/Network/VpcCidr`
- `/MediaResourceManager/Identity/ActiveDirectoryDomainName`
- `/MediaResourceManager/Identity/ActiveDirectoryServerIP1`
- `/MediaResourceManager/Identity/ActiveDirectoryServerIP2`
- `/MediaResourceManager/Identity/StudioAdminActiveDirectoryLoginCredentials` (Secrets Manager)

**Implementation Notes**:
1. **Environment Variable**: Pass `PRODUCT_NAME` environment variable to `GenerateFsxTemplateFunction`
2. **Parameter Creation**: Create new SSM parameters during deployment using the pascalCase naming
3. **Template Generation**: Use the productName to build parameter paths dynamically
4. **User Configuration**: FSx parameters (storage, throughput, backup retention) come from user input
5. **Infrastructure Parameters**: Network and identity parameters come from SSM using productName prefix

```javascript
    await dynamodb.put({
      TableName: process.env.STORAGE_TABLE_NAME,
      Item: {
        storageId,
        name,
        type: 'fsx-windows',
        status: 'initializing',
        storageCapacity: configuration.ssdStorageCapacity,
        throughput: configuration.throughputCapacity,
        backupRetention: configuration.automaticBackupRetentionPeriod,
        createdAt: new Date().toISOString()
      }
    }).promise();
    
    // 2. Start Step Functions execution
    await sfn.startExecution({
      stateMachineArn: process.env.STORAGE_CREATION_STATE_MACHINE_ARN,
      input: JSON.stringify({
        storageId,
        name,
        configuration
      }),
      name: `storage-creation-${storageId}-${Date.now()}`
    }).promise();
    
    // 3. Return immediate response
    return {
      statusCode: 200,
      headers: corsHeaders,
      body: JSON.stringify({ storageId, status: 'initializing' })
    };
    
  } catch (error) {
    console.error('Error starting storage creation:', error);
    return {
      statusCode: 500,
      headers: corsHeaders,
      body: JSON.stringify({ error: 'Failed to start storage creation' })
    };
  }
};
```

#### Status Flow with Native DynamoDB Updates

**Status Progression** (Updated by Step Functions directly):
1. **initializing** → Initial record created by CreateStorageFunction
2. **validating** → Step Functions validates parameters
3. **creating** → CloudFormation stack deployment started
4. **available** → FSx file system ready for use
5. **failed** → Creation failed, error details logged
